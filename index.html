Why Codex CLI Can't See Your API Key
(Even Though It's Set)

A debugging story about a config field that looks like it points to a file, an environment variable that really is set, and a background daemon that quietly outlived the fix.

OpenAI Codex CLI env vars app-server daemon Linux / bash OpenAI-compatible gateways

The symptom

Codex CLI (@openai/codex) was configured to talk to a local OpenAI-compatible gateway instead of OpenAI directly, via a custom model provider in ~/.codex/config.toml: 

[model_providers.my_gateway]
name = "My Gateway"
base_url = "http://localhost:PORT/v1"
env_key = "MY_GATEWAY_API_KEY"
requires_openai_auth = false

Opening a terminal and running codex produced:

>_ OpenAI Codex (v0.158.0)

■ Missing environment variable: `MY_GATEWAY_API_KEY`.

Except the variable was set — echo $MY_GATEWAY_API_KEY printed it fine, it was exported in ~/.bashrc, and even codex doctor reported it as present. Closing and reopening the terminal didn't help. This is the trail that led to the actual cause, which had nothing to do with the variable being unset.

Misconception #1: env_key does not point to a file

It's tempting to read env_key = "MY_GATEWAY_API_KEY" and assume Codex resolves that against some .env file it knows about. It doesn't. env_key is nothing more than the name of an environment variable. At request time Codex does the equivalent of: 

std::env::var("MY_GATEWAY_API_KEY")

against its own process environment — whatever was inherited from the shell that launched it. Codex CLI has no built-in .env loader. If you keep your key in a .env file, nothing reads it into the process unless something else does that work first.

Fix, part 1: make the shell responsible for loading the file before Codex ever starts. A small wrapper function in ~/.bashrc does the job and keeps the key out of version-controlled dotfiles:

# ~/.env (0600 permissions, not committed anywhere)
MY_GATEWAY_API_KEY=sk-xxxxxxxxxxxxxxxxxxxx

# ~/.bashrc
mytool() {
    if [ -f "$HOME/.env" ]; then
        set -a          # auto-export everything sourced below
        . "$HOME/.env"
        set +a
    fi
    command mytool "$@"   # hand off to the real binary on PATH
}

A bash function with the same name as the binary shadows it for interactive shells, reloading the .env file fresh on every invocation — so rotating the key later only means editing one file, not re-exporting anything anywhere.

That fix was verified two different ways: codex doctor reported provider auth env var  MY_GATEWAY_API_KEY (present), and a one-shot codex exec "..." round-tripped a real completion through the gateway. Both worked. The interactive TUI, run in the very same terminal, right after, still failed with the exact same "missing environment variable" error.

Misconception #2: a working shell means a working session

That contradiction — doctor and exec succeeding, the interactive TUI failing, all in one shell, all with the same freshly-exported variable — is the actual interesting part of this story. It meant the interactive command path wasn't reading the current process's environment at all.

Codex CLI ships with a background process architecture. Its own --help output says as much, in passing: 

Commands:
  agents   Browse all agent sessions on the shared local app-server daemon
  app-server   Run the app server or related tooling
  remote-control   [experimental] Manage the app-server daemon with remote control enabled

ps aux | grep codex confirmed it: a long-lived codex app-server --managed-daemon process, running detached from any terminal, alongside a pid-update-loop helper. 

mfk  3309306  ... codex app-server --listen unix:// --managed-daemon      (started 11:58)
mfk  3349794  ... codex app-server daemon pid-update-loop                 (started 12:09)

Reading /proc/<pid>/environ for that daemon confirmed the theory: no MY_GATEWAY_API_KEY anywhere in it. The daemon had been started earlier — before the key was ever exported anywhere — and every new terminal since then was simply connecting to that same pre-existing daemon over a Unix socket instead of starting a fresh process. New shells, new exports, even a full reboot of the terminal emulator: none of it mattered, because none of it touched the daemon that was actually serving the interactive session.

codex doctor and codex exec, on the other hand, appear to run as self-contained one-off processes that read their own environment directly — which is why they looked healthy while the interactive TUI, going through the daemon, stayed broken.

The trap in one sentence: a tool can hold a cached environment snapshot from whenever its background process was first started, and no amount of "fixing" your shell's environment afterward will reach a process that already exists and communicates over IPC instead of re-reading its environment.

Diagnosis checklist

1
Confirm the variable is really in the current shell.
env | grep MY_KEY
2
Check for a background/daemon process for the tool.
ps aux | grep -i <toolname> — look for anything with no controlling TTY (TTY column showing ?) that's older than your current terminal.
3
Read that process's actual environment, not yours.
tr '\0' '\n' < /proc/<pid>/environ | grep MY_KEY
If your shell has the variable but this doesn't, you've found a stale cached-environment daemon.
4
Kill it and let the tool respawn a fresh one.
kill <pid>, then re-run the tool from a shell that has the correct environment. Confirm no daemon-ish process is left running with the old PID before retrying.

Why this matters beyond Codex

Nothing here is specific to Codex, OpenAI, or any particular gateway. Any CLI with a "start once, reuse a daemon for speed" architecture — language servers, dev-tool daemons, build caches, IDE backends — can exhibit exactly this symptom: environment changes that are correct in every new shell, yet invisible to the tool, because the tool isn't reading a fresh environment at all. It's talking to a process that was born before your fix existed.

The general debugging move is the same regardless of tool: separate "is the variable set in my shell" from "is the variable set in the environment of the process actually handling my request." Those can silently diverge the moment a long-lived background process enters the picture, and most CLIs don't advertise that they have one.
